## 6. Database Architecture

Use MySQL as the source of truth.

Follow database-per-service architecture.

Requirements:

- Each microservice owns its business database.
- Never allow one microservice to directly access another microservice's database.
- Avoid shared database tables between services.
- Use Flyway for database version management.
- Use proper primary keys, foreign keys within service boundaries, indexes, and constraints.
- Use transactions for business-critical operations.
- Implement idempotency for critical APIs.
- Use optimistic locking wherever appropriate.
- Explain eventual consistency and distributed transaction handling.
- use apche debizium connector for CDC from mysql to Elasticsearch. Example Product write data (mysql) and read data (Elasticsearch)

For local development, allow a single MySQL server/container with separate databases for individual microservices to reduce resource consumption.

For production, support independent databases or appropriately isolated database instances based on service requirements.

## 8. Real-Time Stakeholder Updates

This is one of the most important requirements.

Whenever a stakeholder performs a relevant business operation, other authorized stakeholders should receive real-time updates without refreshing the React application.

Examples:

- Vendor updates product stock: relevant customer and admin screens receive availability updates.
- Restaurant accepts an order: customer and admin dashboards receive updates.
- Customer places an order: restaurant receives an incoming order notification.
- Delivery partner accepts an assignment: restaurant, customer, and admin receive appropriate updates.
- Delivery partner updates delivery status: customer receives the latest status.
- Admin suspends a vendor: affected vendor operations are updated appropriately.

Design the solution using:

- Kafka for internal event distribution.
- WebSocket or Server-Sent Events for frontend updates.
- Notification Service for stakeholder-specific notifications.
- Redis where appropriate for connection coordination and temporary state.

Explain how to support multiple backend replicas and reconnecting clients.

Ensure users receive only notifications they are authorized to see.

Do not broadcast every event to every user.

### Human Approval Requirements

Implement human approval wherever an operation is sensitive or has financial or operational consequences.

Examples:

- Customer confirms final purchase.
- Vendor confirms sensitive product or pricing changes.
- Restaurant owner approves exceptional order decisions.
- Delivery manager approves sensitive delivery reassignment.
- Admin approves refunds, account suspension, and sensitive administrative operations.

Design an approval lifecycle:

PENDING_APPROVAL → APPROVED → EXECUTING → COMPLETED

Also support:

REJECTED, EXPIRED, FAILED, and CANCELLED.

Important rules:

- AI must not bypass authorization.
- AI must not approve its own actions.
- Backend services must validate approval before execution.
- Approval must be bound to the exact proposed action and its parameters.
- Prevent duplicate execution.
- Record who approved, what was approved, and when.
- Provide a clear explanation of the action before requesting approval.

Explain which operations can be executed automatically and which require human approval.

Do not build an uncontrolled autonomous agent that can execute arbitrary business operations.

## 19. Important Architectural Rules

Follow these rules throughout the project:

- MySQL is the source of truth for transactional business data.
- Each microservice owns its database.
- Microservices must be independently deployable.
- Never use shared database tables between services.
- Never perform direct cross-service database access.
- Prefer asynchronous communication for business events.
- Use synchronous REST APIs only where an immediate response is genuinely required.
- Use the Outbox Pattern for reliable event publishing.
- Implement idempotency and retry handling.
- Never allow AI agents to bypass business rules.
- Enforce human approval on sensitive operations.
- Keep code simple, readable and maintainable.
- Avoid unnecessary abstractions.
- Avoid premature optimization.
- Do not introduce technologies without explaining their purpose.
- Preserve existing functionality if an existing application is present.
